# DayBoard Google OAuth verification plan

Get DayBoard 1.0 verified for Calendar and Tasks in a new production Google Cloud project, and treat Gmail as a later, separate restricted-scope review.

Prepared 2026-09-23 from this repo's code and the pages listed at the end, all read that day. Not legal advice. The consent screen was observed in **Testing** on 2026-09-22 (100 test users at most; sign-ins expire after 7 days). No verification request is confirmed submitted.

## Key points

- **1.0 scopes:** `openid`, `email`, `calendar.events`, `calendar.calendarlist.readonly` and `tasks`. None is on Google's restricted list ([restricted scopes](https://support.google.com/cloud/answer/13464325)), so 1.0 needs brand verification and sensitive-scope verification for whichever scopes Google marks sensitive (probably at least `calendar.events`; the exact labels are provisional, see 1.1), but no security assessment, which Google ties to restricted scopes ([requirements](https://support.google.com/cloud/answer/13464321)). Dropping `gmail.modify` is what takes the assessment question out of 1.0.
- **Use two Cloud projects.** Google requires separate test and production projects ([policy compliance](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance)). Keep the current project in Testing for the Gmail beta and create a production project with its own Desktop client for 1.0. A production project whose build asks for an unapproved scope shows the unverified-app screen and uses up a 100-user cap that lasts for the project's lifetime ([FAQ](https://support.google.com/cloud/answer/13463817), [app audience](https://support.google.com/cloud/answer/15549945)). Beta and 1.0 builds share one token store, so 1.0 must not reuse a beta tester's Gmail-capable token (4.4).
- **The domain blocks most steps:** homepage, privacy-policy URL, Search Console verification, brand verification, the demo video and the verification request.
- **Not blocked:** declaring the scopes on the production project's Data Access page, a Google-branded sign-in button, an in-app disclosure and consent step, a check of which scopes the user granted, tokens tied to the production client, the AI provider check, the Gmail-free 1.0 build, privacy-policy fixes and a support email.
- **AI matters for 1.0 too.** Google's Limited Use rules cover data from sensitive Workspace scopes, not only Gmail. Sending Calendar or Tasks data to an AI provider needs a prominent feature, the user's consent, and no model training beyond that user ([Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)). The user picking the provider doesn't change this, so check each provider's training and retention terms before offering it with Google data (2.5). The Assistant also runs tools on MCP servers the user added without asking, so those servers can receive Google data; 1.0 needs per-call confirmation or those servers off in Google-data conversations (checklist 11).
- **Launch gate:** 1.0 and Product Hunt also wait for Miles's approval of the website; Google's approval alone isn't enough (checklist 23).
- **Gmail later:** restricted review, and possibly a yearly security assessment paid to an outside assessor. Whether DayBoard needs one is unresolved; ask Google (4.2). Google doesn't support incremental authorization for installed apps, so turning on Mail means a second full sign-in ([installed-app guide](https://developers.google.com/identity/protocols/oauth2/native-app)).

## 1. Current state

Sign-in lives in `main/services/google-auth.ts`: one `SCOPES` list sent with `access_type=offline`, `prompt=consent` and `include_granted_scopes=true` through the PKCE loopback flow in `main/services/google-loopback-oauth.ts` (Desktop client, `127.0.0.1` redirect). API calls are in `main/services/google-api.ts`; IPC handlers in `main/handlers/productivity.ts` and `main/handlers/item-editing.ts`; the local MCP server in `main/services/mcp-http-server.ts`.

The code never sends mail, deletes or trashes messages, creates, renames or deletes labels, or changes settings. It does change which labels a message carries: archive removes `INBOX` and mark read removes `UNREAD`. It does copy mail-derived text into Google Tasks when the user clicks Add task (last row), and the Assistant can do the same through suggested items (1.3).

- `gmail.modify` is the narrowest single scope that covers today's Mail features. What it grants is broader than what DayBoard does: Google describes it as permission to read, compose and send email ([Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)), and the consent screen will show that. DayBoard only lists, reads, saves drafts, archives and marks read; it has no send call. Miles should accept that gap knowingly, or drop archive and mark read and use the narrower pair below.
- `gmail.readonly` plus `gmail.compose` covers reading and drafts but not archive or mark read, and `gmail.compose` also allows sending ([Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)). `gmail.metadata` can't search or read message bodies.
- Every Gmail scope a standalone app can use to search an inbox or read message bodies is restricted, so narrowing wouldn't avoid the restricted review. Google also lists add-on scopes that read messages as sensitive or non-sensitive (`gmail.addons.current.message.readonly`, `gmail.addons.current.message.action`), but they cover only messages the user opens inside a Google Workspace add-on ([Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)), so they don't fit a Mac app. The only way to narrow is to drop archive and mark read.

### 1.3 Where Google data goes

- **Google APIs:** called directly from the Mac. DayBoard runs no server that receives Google data. Tokens are encrypted with Electron `safeStorage` (`main/platform/oauth-store.ts`). Sign-out asks Google to revoke the token, then deletes it from the Mac whether or not revocation worked; `disconnectGoogle` doesn't check Google's response and logs only network errors.
- **Copies into Tasks, Calendar or Reminders, at the user's click:** Add task copies an email's subject and Gmail link into Google Tasks (1.2). The Assistant can suggest items (task, reminder or event) whose title and notes the model writes from the calendar, task and mail data it sees; clicking Add creates them in Google Tasks, Google Calendar or Apple Reminders (`addAction` in `renderer/main/assistant-view.tsx`).
- **AI providers:** off by default (`ai.enabled: false` in `main/services/settings-store.ts`). Prompts are built in `renderer/lib/ai-prompts.ts` and go through the provider's command-line tool on the Mac (Claude Code, Codex, Gemini CLI or Muse; `main/services/ai/cli-providers.ts`) or straight to the provider with the user's API key (OpenAI, Anthropic, Google, xAI, Mistral, DeepSeek, Groq or OpenRouter; `main/services/ai/api-providers.ts`).

- **User-added MCP servers in the Assistant:** with "Use MCP in Assistant" on (the default) and the Claude Code, Codex or API-key path, every enabled server from Settings, MCP is passed to the model (`resolveAssistantMcpServers` in `main/services/ai/assistant-mcp.ts`, `runAssistant` in `main/services/ai/assistant.ts`). Nothing asks the user before a tool runs: the Claude Code path allows every tool on each server (`--allowedTools` in `main/services/ai/cli-providers.ts`), Codex runs with `approval_policy="never"`, and the API path executes tool calls directly. A server can be a local command or a remote URL, and the model writes the tool arguments, so Calendar, Tasks or mail text from the snapshot can reach that server and whoever runs it. Gemini CLI and Muse get no MCP servers.
- **Local MCP server:** off by default. When on, MCP clients on the Mac can read Tasks, Reminders, Gmail and Calendar and, with "allow writes" on, create items, draft replies, archive and mark read. It listens on `127.0.0.1` and needs an access key.
- **Local copies:** AI results (briefing, priorities, triage, meeting prep, weekly review) and Assistant chats are saved on the Mac (`renderer/lib/storage.ts`, `main/services/assistant-history-store.ts`). No code clears them at sign-out.

### 2.2 Brand verification

Needed because DayBoard's project is External, will be In production and should show its name and logo ([brand guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification)).

- **Homepage:** public, on a domain you've verified, clearly about DayBoard, describes what the app does (not only a sign-in page) and links to the privacy policy with the same URL as the consent screen ([requirements](https://support.google.com/cloud/answer/13464321)).
- **Privacy policy:** on the homepage's domain, linked from the homepage and the consent screen, and says how the app accesses, uses, stores and shares Google user data ([sensitive-scope guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification)). See 3.5.
- **Authorized domains:** list the top private domain used by the homepage, privacy and terms URLs, and verify it in Google Search Console with an account that is Owner or Editor on the Cloud project ([brand guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification)). That account must also be a verified owner in Search Console ([unverified apps](https://support.google.com/cloud/answer/7454865)). A Domain property is verified with a DNS record, and verifying the root domain covers its subdomains ([Search Console](https://support.google.com/webmasters/answer/9008080)). Only Web clients' redirect URIs and origins must be listed, so the Desktop client's `127.0.0.1` redirect adds no domain ([brand guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification)).
- **App name, logo, support email, developer contact:** must accurately represent the app. Keep project Owners, Editors and contact emails current; Google's review team writes to them ([sensitive-scope guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification), [policy compliance](https://developers.google.com/identity/protocols/oauth2/production-readiness/policy-compliance)).
- **Google-branded sign-in button:** the button that starts the grant must follow Google's branding guidelines ([requirements](https://support.google.com/cloud/answer/13464321)). The guidelines say this is required for verification and fix the full-color "G" logo, colors and font ([branding guidelines](https://developers.google.com/identity/branding-guidelines)). DayBoard's buttons that start sign-in are plain buttons: `renderer/components/source-gate.tsx`, `renderer/settings/account-settings.tsx` ("Sign in with Google", "Sign in again") and `renderer/settings/sources-tab.tsx` ("Reconnect").
- **Process:** Branding page, then Verify Branding. The automated check usually takes minutes; a manual review usually 2–3 business days. Publish a passing result within 7 days or run it again. Branding can't be edited during a review, and it must be published before you request data-access verification ([brand guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification), [sensitive-scope guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification)). Declaring scopes doesn't wait for it: Google has you add and classify scopes while configuring the consent screen, before publishing ([submitting](https://support.google.com/cloud/answer/13461325)).

### 2.3 Sensitive-scope verification

- Declare every requested scope on the Data Access page. Request only the narrowest scopes, and none for features that aren't built yet ([sensitive-scope guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification), [requirements](https://support.google.com/cloud/answer/13464321)).
- Justify each sensitive scope, including why a narrower scope won't work and what would break ([requirements](https://support.google.com/cloud/answer/13464321)). Drafts are in 3.2.
- The use must be appropriate; Google names productivity purposes as the usual approved kind ([requirements](https://support.google.com/cloud/answer/13464321)).
- Demo video ([sensitive-scope guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification), [requirements](https://support.google.com/cloud/answer/13464321)):
  - uploaded to YouTube as **Unlisted**;
  - shows the whole grant flow, including sign-in, in **English**, with the consent screen's language menu (bottom left) set to English;
  - shows the same app and branding being submitted, including the app name on the consent screen;
  - shows the OAuth **client ID in the browser address bar** of the consent screen;
  - shows the complete consent screen with exactly the requested scopes;
  - demonstrates the feature each sensitive scope enables.
- Publish the project to In production, then choose Prepare for Verification; apps in testing aren't verified ([submitting](https://support.google.com/cloud/answer/13461325)). Google suggests deleting OAuth clients that aren't ready for production ([sensitive-scope guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification)).
- Google's Trust & Safety team follows up by email to the developer contacts and the support email ([sensitive-scope guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification)).

### 2.4 Restricted scopes and the security assessment

- **Extra review** on top of the brand and sensitive steps: choose a permitted app type under "What features will you use?", describe why narrower scopes aren't enough, and show every restricted scope, and every OAuth client, in the video ([restricted-scope guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)). Gmail's approved uses include email clients and apps that improve email for productivity, such as generative AI summaries ([Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)).
- **Security measures** required for restricted scopes include encryption in transit and at rest, encrypted OAuth tokens, managed keys and prompt-injection protection ([Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)).
- **When the assessment (CASA) applies.** Google's pages word it differently:
  - Gmail scopes page: required if you "store restricted scope data on servers (or transmit)" ([Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)).
  - Restricted-scope guide: required for apps that can reach restricted data "from or through a third-party server" ([restricted-scope guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)).
  - Help Center: restricted-scope apps need an annual assessment, with no server condition stated ([security assessment](https://support.google.com/cloud/answer/13465431), [requirements](https://support.google.com/cloud/answer/13464321)). The Workspace consent guide also marks restricted scopes as needing an assessment, without conditions ([Workspace consent guide](https://developers.google.com/workspace/guides/configure-oauth-consent)).
  - Both data policies: may depend on the API and the number of users ([User Data Policy](https://developers.google.com/terms/api-services-user-data-policy), [Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)).
- **Cadence:** at least every 12 months from the assessor's letter, a full re-test each year even without changes; Google emails when it's due ([annual recertification](https://support.google.com/cloud/answer/13463816), [FAQ](https://support.google.com/cloud/answer/13463817)). The letter is called a Letter of Assessment on one page and a Letter of Validation on another ([restricted-scope guide](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification), [security assessment](https://support.google.com/cloud/answer/13465431)).
- **Cost:** Google charges nothing; you pay the assessor directly, and Google suggests comparing assessors. The FAQ also mentions a free tier 2 path ([FAQ](https://support.google.com/cloud/answer/13463817)). No prices were checked.
- **Timing:** the assessment is the last step of the restricted review; Trust & Safety tells you when to start ([security assessment](https://support.google.com/cloud/answer/13465431)). The framework is the App Defense Alliance's CASA ([CASA](https://appdefensealliance.dev/casa)).

### 2.5 Limited Use and AI providers

Apply Limited Use to 1.0's Calendar and Tasks data, not only to Gmail. The Workspace policy governs Google Workspace APIs, which is where Google files Calendar and Tasks ([Calendar scopes](https://developers.google.com/workspace/calendar/api/auth), [Tasks scopes](https://developers.google.com/workspace/tasks/auth)), and it says its Limited Use rules cover data derived from both sensitive and restricted scopes ([Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)), and the verification requirements list limited use for sensitive scopes too ([requirements](https://support.google.com/cloud/answer/13464321)). One FAQ answer about privacy-policy wording says only restricted-scope data must meet the User Data Policy's "Additional Requirements for Specific API Scopes" ([FAQ](https://support.google.com/cloud/answer/13463817)). That sentence points to a section of a different document, and that section itself names "Sensitive and Restricted Scopes" and applies unless the product's own policy says otherwise ([User Data Policy](https://developers.google.com/terms/api-services-user-data-policy)). It doesn't exempt Calendar or Tasks data from the Workspace policy.

Allowed:

- Using Google data only for the app's approved use and for features that are visible and prominent in the app ([Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy), [User Data Policy](https://developers.google.com/terms/api-services-user-data-policy)).
- Transferring it, for example to an AI provider, only to provide those features and only with the user's consent. Transfers for security, legal duties or a merger (with prior consent) are also allowed ([Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)).
- AI use only for a personalized model serving that user's feature. The policy bans transferring or using Google data to create, train or improve any model beyond that user's personalized model ([Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)). The FAQ describes a personalized model as one run only on the device or tailored to a single user or organization, without mixing other users' data, and says Google data may not train or improve foundation or frontier models or be stored with them ([FAQ](https://support.google.com/cloud/answer/13463817)).

Not allowed: selling the data, ads, credit decisions, data brokers, or people reading the data without the user's explicit consent (security and legal exceptions apply). Google's terms also bar permanent copies of Google user data, including caches kept longer than the cache header allows ([Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)).

Must disclose:

- A privacy policy that fully documents access, use, storage and sharing, every purpose including secondary ones, and every action taken on the user's behalf ([User Data Policy](https://developers.google.com/terms/api-services-user-data-policy)).
- A Limited Use statement on the website, such as saying DayBoard's use of information from Google APIs follows the User Data Policy, including the Limited Use requirements ([FAQ](https://support.google.com/cloud/answer/13463817), [Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)).
- An **in-app** disclosure shown in normal use (not only in settings or the privacy policy) that names the data and how it's used and shared, right before a consent request that needs an explicit action. No collection before consent ([Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)).
- Help pages on how users manage and delete their data ([Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy)).
- Asking for access in context where possible. The Workspace policy says agentic apps should granularly require users to confirm each MCP, tool, skill or other agent invocation ([Workspace policy](https://developers.google.com/workspace/workspace-api-user-data-developer-policy), [User Data Policy](https://developers.google.com/terms/api-services-user-data-policy)).

What this means for DayBoard (analysis, not Google's words): visible AI features are necessary but not enough. The policy has no exception for the user's choice of provider, so DayBoard answers for what every provider it offers does with Google data. Gaps today:

- No in-app consent step names the provider and the data.
- Not every transfer follows a click: the automatic briefing sends data the first time the Today view opens each day, the Assistant sends a snapshot on every turn, and its tools run without per-call confirmation, including tools on MCP servers the user added, which can receive Google data in their arguments (1.3). That path isn't disclosed anywhere yet.
- No provider's training or retention terms have been read. The code has no on-device model path: API keys go to the providers' hosted endpoints (`main/services/ai/api-providers.ts`), and the command-line tools need the user's provider sign-in (`main/services/ai/cli-providers.ts`). So the FAQ's on-device kind of personalized model doesn't apply, and whether a hosted model answering one request counts as tailored to that user is unconfirmed.

Gate before submitting with AI on Google data: for each provider DayBoard would offer, read and record its training and retention terms for the path DayBoard uses (the provider's Mac app or an API key). Offer Google data only to providers whose terms meet the rules above, and keep it out of every other provider's path (checklist 12). Ask Google about hosted models in the 1.0 submission, reusing the last question in 4.2. Leave the AI note (3.2) out of the submission until this gate and the consent step are done.

Second gate (checklist 11): before any build with Google data ships the Assistant's MCP tools, either ask the user to confirm each tool call that can read or send Google data, showing the server, the tool and its arguments, or turn off user-added MCP servers in the Assistant whenever Google data is in the conversation. Then disclose whichever path remains (3.2, 3.5, 4.3).
